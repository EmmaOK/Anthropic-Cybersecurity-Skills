# Architecture Decision Record (ADR)

The **why** behind this repo's structure. `CLAUDE.md` says *what* the conventions are;
this file records *why* they exist, so a decision isn't silently reversed by someone who
never saw the reasoning. Code structure, skill inventory, and counts are NOT recorded here
— those live in the code and `index.json` (see ADR-0005).

**Conventions for this file:** append-only where practical; one decision per entry; date
each entry (absolute dates); when a decision is superseded, mark it and add a new entry
rather than editing history. Entries 0001–0011 were reverse-engineered from the established
codebase and documented on 2026-06-20.

---

## ADR-0001 — Skills follow the agentskills.io open standard
**Decision:** Each skill is a directory `skills/<kebab-name>/` with a required `SKILL.md`
(YAML frontmatter + ordered body sections) and an Apache-2.0 `LICENSE` copy; optional
`references/` and `scripts/agent.py`.
**Why:** Conformance to the open standard makes every skill portable across Claude Code,
Cursor, GitHub Copilot, and 23+ other agent platforms with no per-platform rework — the
library's reach is the whole point.
**Implications:** Frontmatter schema is fixed (see `CLAUDE.md`); body sections have a
required order; new skills must copy `LICENSE` in.

## ADR-0002 — Fixed 26-subdomain taxonomy; `ai-security` is an accepted *extension*, not a 27th
**Decision:** Skills use one of the 26 standard subdomains. AI/agentic-security skills use
`subdomain: ai-security`, which is deliberately **not** added to the official 26 list.
**Why:** The 26 are the standard's canonical set; adding to it would break portability and
the standard's contract. `ai-security` is a documented local extension so the ~50 AI skills
can be grouped without polluting the canonical taxonomy.
**Implications:** Do not add `ai-security` to the official 26 anywhere. Validation accepts it
as an extension only.

## ADR-0003 — AI-security skills use framework-specific name prefixes
**Decision:** Naming maps to the source framework — `llm-*` (OWASP LLM Top 10), `mcp-*`
(OWASP MCP Top 10), `agent-*`/`agentic-*`/`rogue-*`/`human-agent-*`/`securing-inter-*`
(OWASP Agentic Top 10), `performing-maestro-*`/`rag-pipeline-*`/`ai-*` (MAESTRO).
**Why:** The prefix makes a skill's framework lineage greppable and keeps the four AI
frameworks' coverage auditable at a glance (`grep -l "subdomain: ai-security"`).
**Implications:** New AI skills must match the prefix table in `CLAUDE.md`.

## ADR-0004 — MITRE ATT&CK technique IDs live in `tags`, not a dedicated field
**Decision:** ATT&CK technique IDs (e.g. `T1059.001`) go in the `tags` array. Other
frameworks (ATLAS, D3FEND, NIST CSF, NIST AI RMF) get dedicated frontmatter fields.
**Why:** ATT&CK techniques are high-cardinality and overlap heavily with keyword tags;
a dedicated field would duplicate tag search. The other frameworks are low-cardinality
mappings worth querying as first-class fields.
**Implications:** Don't add an `attack_techniques` field; search ATT&CK via `tags`.

## ADR-0005 — `index.json` is the single source of truth for skill inventory; prose counts are approximate
**Decision:** `index.json` is autogenerated by CI (`update-index.yml`) and is the canonical
skill catalog. Skill counts in `CLAUDE.md` and docs are explicitly approximate; the library
grows continuously.
**Why:** A hand-maintained count drifts the moment a skill is added. Pinning truth to a
generated file removes a whole class of "the docs say 800 but there are 831" inconsistencies.
**Implications:** Never hand-edit `index.json`. Never assert an exact count in prose — say
"800+" and point readers to `find skills -name SKILL.md | wc -l` or `index.json`.

## ADR-0006 — CI is inline Python on `ubuntu-latest`; no npm, Makefile, or build tooling
**Decision:** All three workflows (`validate-skills`, `update-index`, `sync-marketplace-version`)
embed their logic as inline Python 3. There is no package manager manifest or build system.
**Why:** A skill library is data, not an application. Inline Python keeps the toolchain
zero-install and the validation logic visible in one place, with no dependency supply chain.
**Implications:** To run validation locally, extract the embedded Python from the workflow.
Don't introduce a `package.json`/`Makefile` without revisiting this.

## ADR-0007 — MCP servers fail closed and stay registered
**Decision:** The 7 servers in `.mcp.json` load on launch from the repo root; backend-dependent
ones (`infra`, `dast`, `burp-pentest`, etc.) fail closed when their backend is unreachable.
**Why:** Failing closed means a missing backend is a no-op, not a hazard — so the full set can
stay registered for every contributor without anyone accidentally acting against a live system.
**Implications:** Safe to leave all servers registered. Secrets come from shell env vars, never
committed (`.mcp.json` defaults are placeholders — see ADR-0008).

## ADR-0008 — Hardening conventions are mandatory in all scripts
**Decision:** Scripts must: read credentials from env vars (never hard-code); honor
`SKIP_TLS_VERIFY` rather than disabling TLS unconditionally; annotate any `pickle.load` with
`# nosec B301` + a trusted-source note; depend only on stdlib + `anthropic` (guard optional
imports); be self-contained (no cross-skill imports); use `argparse` with `--output`; and
`sys.exit(1)` on HIGH/CRITICAL so they gate CI.
**Why:** The library is offensive-security tooling shipped to many users — a single
hard-coded key or silently-disabled TLS check would be a real exposure. Uniform conventions
make the static audit (`skill_security_audit.json`) meaningful.
**Implications:** New `scripts/agent.py` files are reviewed against this list. See
`CLAUDE.md` → Security Conventions.

## ADR-0009 — Project identity: community-maintained, Apache-2.0, not affiliated with Anthropic
**Decision:** Display name "Cybersecurity Skills"; the GitHub repo slug keeps the original
`Anthropic-Cybersecurity-Skills` name. Independently maintained; Apache-2.0.
**Why:** The original name predates the rename; changing the slug would break every existing
clone/link. The "not affiliated with Anthropic PBC" note prevents misattribution given the
name.
**Implications:** Keep the non-affiliation note prominent; don't imply official endorsement.

## ADR-0010 — `marketplace.json` version is bumped automatically on release
**Decision:** `.claude-plugin/marketplace.json` version is set by `sync-marketplace-version.yml`
when a GitHub release is published — not edited by hand.
**Why:** Ties the published plugin version to the release event, removing manual version drift.
**Implications:** Don't hand-edit the version in `marketplace.json`.

## ADR-0011 — Phantom standardizes on `claude-opus-4-8`
**Decision:** Every Phantom module (`phantom/*.py`) uses model id `claude-opus-4-8` for its own
reasoning. (`claude-sonnet-4-6` appears only as an *example target model* for the garak
scanner, not as Phantom's own model.)
**Why:** Consistent capability/behavior across the interactive REPL, the orchestrator, and the
SDK spike; one place to bump when migrating models.
**Implications:** New Phantom code uses `claude-opus-4-8`. See `phantom/CLAUDE.md` for the
agent architecture and the Agent SDK port direction.

## ADR-0012 — Phantom is being evolved into an autonomous, task-assignable agent
**Decision:** Direction (set 2026-06-19): make Phantom accept a high-level task + scope and
run it end-to-end via the skill library, rather than being walked through steps interactively.
The leading approach is porting onto the **Claude Agent SDK** (`phantom/phantom_sdk.py` spike).
**Why & details:** See `phantom/CLAUDE.md` (architecture, the SDK spike, the safety gate, and
the venv/runtime situation). Recorded here as the cross-cutting direction; specifics live with
the subsystem.
**Implications:** New autonomous-agent work should prefer the SDK-managed loop over extending
the hand-rolled `run_turn()` in `main.py`.
