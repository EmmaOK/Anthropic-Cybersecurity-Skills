# Configuring Wazuh Custom Syslog Detection Rules

## When to Use

- When building detection rules for Linux simulation scripts that use `logger` to emit syslog events
- When custom Wazuh rules are not firing despite being syntactically valid
- When `custom_rules.xml` or `local_rules.xml` appears to be silently ignored
- When building a SOC training lab that needs staged, labelled detections per attack phase
- When validating rule logic with `wazuh-logtest` before deploying to production

**Do not use** `<decoded_as>syslog</decoded_as>` with `<program_name>` rules — these are mutually exclusive decoder paths in Wazuh 4.x.

## Prerequisites

- Wazuh Manager 4.x running
- Access to `ossec.conf` and the `ruleset/` directory
- Understanding of Wazuh XML rule syntax
- Linux `logger` command on monitored endpoints for testing

## Workflow

### Step 1: Understand How Wazuh Decodes Syslog Events

When Wazuh logcollector reads `/var/log/syslog` or `/var/log/auth.log`, it passes lines through the syslog decoder. The syslog decoder extracts the `program_name` field from the syslog tag.

When a script calls `logger -t mytag "MY MESSAGE"`, Wazuh sees:
- `predecoder.program_name`: `mytag`
- `full_log`: the full syslog line including the message

Rules can match on `<program_name>` (exact tag) and `<match>` (substring in the full log).

### Step 2: Structure custom_rules.xml Correctly

**Critical requirement**: All custom rules must be inside a **single** top-level `<group>` element. Wazuh silently ignores any second `<group>` block in the same file.

```xml
<!-- custom_rules.xml — ALL rules in ONE group -->
<group name="custom_soc,lab_simulation,">

  <!-- Original custom rules -->
  <rule id="100010" level="5">
    <if_sid>5501</if_sid>
    <description>Custom: user account created</description>
  </rule>

  <!-- Lab simulation rules — match logger-emitted syslog events -->
  <!-- Stage 1: Discovery (T1082, T1033) -->
  <rule id="100200" level="5">
    <program_name>^lab2-attacker$</program_name>
    <match>DISCOVERY</match>
    <description>Lab2 Sim: Stage 1 — System discovery commands executed</description>
    <mitre>
      <id>T1082</id>
      <id>T1033</id>
    </mitre>
    <group>lab2,discovery,</group>
  </rule>

  <!-- Stage 2: Credential access (T1552.001) -->
  <rule id="100201" level="7">
    <program_name>^lab2-attacker$</program_name>
    <match>CREDENTIAL_ACCESS</match>
    <description>Lab2 Sim: Stage 2 — Credential files accessed</description>
    <mitre>
      <id>T1552.001</id>
    </mitre>
    <group>lab2,credential-access,</group>
  </rule>

  <!-- Stage 4: Staging (T1074.001) -->
  <rule id="100400" level="6">
    <program_name>^lab2-attacker$</program_name>
    <match>STAGING</match>
    <description>Lab2 Sim: Stage 4 — Data staged for exfiltration</description>
    <mitre>
      <id>T1074.001</id>
    </mitre>
    <group>lab2,collection,</group>
  </rule>

</group>
```

**Key syntax rules:**
- `<program_name>^tagname$</program_name>` — anchored regex match on the syslog tag
- `<match>KEYWORD</match>` — case-sensitive substring match on the full log line
- Do NOT add `<decoded_as>syslog</decoded_as>` — it conflicts with `<program_name>`
- Rule IDs 100000–109999 are reserved for local/custom rules

### Step 3: Register the Rule Files in ossec.conf

Custom rule files must be explicitly listed in the `<ruleset>` section of `ossec.conf`. Without this, Wazuh loads the rule file but does not activate the rules:

```xml
<ossec_config>
  <ruleset>
    <decoder_dir>ruleset/decoders</decoder_dir>
    <rule_dir>ruleset/rules</rule_dir>
    <rule_exclude>0215-policy_rules.xml</rule_exclude>

    <!-- These lines are required — mounted files are not auto-included -->
    <rule_include>etc/rules/local_rules.xml</rule_include>
    <rule_include>etc/rules/custom_rules.xml</rule_include>

    <list>etc/lists/audit-keys</list>
  </ruleset>
</ossec_config>
```

The path is relative to `/var/ossec/` inside the Wazuh manager container. If using Docker, mount rule files to `/var/ossec/etc/rules/`.

### Step 4: Reload Wazuh After Changes

After modifying rules or ossec.conf:

```bash
# Reload only analysisd (picks up rule changes but NOT new <localfile> entries)
docker exec soc-wazuh-manager /var/ossec/bin/wazuh-control reload

# Full restart (required for new <localfile> entries and ossec.conf changes)
docker exec soc-wazuh-manager /var/ossec/bin/wazuh-control restart

# Check for XML syntax errors in logs
docker exec soc-wazuh-manager grep -i "error\|invalid" /var/ossec/logs/ossec.log | tail -20
```

### Step 5: Validate Rules with wazuh-logtest

Before deploying to production, test rules against sample log lines using `wazuh-logtest`:

```bash
docker exec -it soc-wazuh-manager /var/ossec/bin/wazuh-logtest
```

At the prompt, paste a sample syslog line matching the format your logger-based script would produce:

```
# Input to wazuh-logtest:
Jun 01 13:51:04 hostname lab2-attacker: STAGE:DISCOVERY scanning system - uname id who ps aux executed

# Expected output:
**Phase 1: Completed pre-decoding.
        full event: 'Jun 01 13:51:04 hostname lab2-attacker: STAGE:DISCOVERY ...'
        timestamp: 'Jun 01 13:51:04'
        hostname: 'hostname'
        program_name: 'lab2-attacker'
        log: 'STAGE:DISCOVERY scanning system ...'

**Phase 2: Completed decoding.
        name: 'syslog'
        program_name: 'lab2-attacker'

**Phase 3: Completed filtering (rules).
        id: '100200'
        level: '5'
        description: 'Lab2 Sim: Stage 1 — System discovery commands executed'
        groups: '["custom_soc", "lab_simulation", "lab2", "discovery"]'
        firedtimes: '1'
```

If Phase 3 shows no rule match, check:
1. Is the `program_name` in the log exactly matching `^lab2-attacker$` (case-sensitive)?
2. Is the `DISCOVERY` keyword present in the log line?
3. Are both rule files listed in `<rule_include>` in ossec.conf?
4. Is there only one `<group>` block in `custom_rules.xml`?

### Step 6: Generate Test Events with logger

On a monitored Linux endpoint, emit test events using the `logger` command:

```bash
# Emit a discovery event matching rule 100200
logger -t lab2-attacker "STAGE:DISCOVERY scanning system - uname id who ps aux executed"

# Emit a credential access event matching rule 100201
logger -t lab2-attacker "STAGE:CREDENTIAL_ACCESS cat /etc/passwd /etc/shadow SSH keys accessed"

# Emit a staging event matching rule 100400
logger -t lab2-attacker "STAGE:STAGING collected files compressed to /tmp/loot.tar.gz"
```

### Step 7: Verify Alerts in OpenSearch

In Wazuh Dashboard or OpenSearch, search for events using:

```
# Find by program tag
predecoder.program_name: lab2-attacker

# Find by keyword in full log
full_log: *DISCOVERY*

# Find by rule group
rule.groups: lab2

# Find by specific rule ID
rule.id: 100200
```

## Key Concepts

| Term | Definition |
|------|------------|
| **program_name** | The syslog tag extracted by Wazuh from the log line (e.g., the value passed to `logger -t`); used for rule matching via `<program_name>` |
| **Single group requirement** | Wazuh silently ignores any second `<group>` block in a rule file; all rules must be inside one top-level `<group>` |
| **rule_include** | ossec.conf directive that explicitly loads a custom rule file; files mounted to `/var/ossec/etc/rules/` are NOT automatically included |
| **wazuh-logtest** | Interactive tool for testing decoder/rule logic against sample log lines without restarting Wazuh |
| **wazuh-control reload** | Restarts only analysisd; picks up rule changes but does NOT restart logcollector — new `<localfile>` entries require a full restart |

## Tools & Systems

- **Wazuh Manager 4.x**: SIEM manager; processes rules via analysisd and reads logs via logcollector
- **wazuh-logtest**: Built-in Wazuh tool for validating rule logic interactively
- **logger**: Linux command for writing to syslog with a custom tag; use `logger -t <tag> "<message>"` in simulation scripts
- **ossec.conf**: Wazuh manager configuration file; controls rule loading, log sources, and integrations

## Common Scenarios

### Scenario: Custom Rules Not Firing Despite Correct XML Syntax

**Symptom**: Rules are in `custom_rules.xml`, XML is valid, but alerts never appear in OpenSearch.

**Diagnosis checklist:**
1. `grep rule_include /var/ossec/etc/ossec.conf` — are both rule files listed?
2. `grep -c "<group" /var/ossec/etc/rules/custom_rules.xml` — is the count > 1? If so, merge into one group.
3. `wazuh-logtest` — does the rule fire against a sample log line?
4. `grep ossec.log -i "custom_rules\|error"` — are there loading errors?

**Most common cause**: Two `<group>` elements in the XML file — Wazuh loads the first and silently ignores the second. Merge all rules under a single `<group name="custom_soc,lab_simulation,">`.

### Scenario: Building Staged Attack Detection for a SOC Training Lab

**Context**: A SOC training lab needs to detect each phase of a post-exploitation attack separately so students can observe individual alerts per MITRE ATT&CK technique.

**Approach**:
1. Write a sim script that calls `logger -t lab2-attacker "STAGE:DISCOVERY ..."` for each phase
2. Write one rule per stage in `custom_rules.xml`, each matching the phase keyword
3. Assign MITRE ATT&CK IDs to each rule for automatic ATT&CK matrix population in Wazuh dashboard
4. Have students filter by `rule.groups: lab2` to see all stages, or by `full_log: *DISCOVERY*` for a specific phase

## Output Format

Wazuh alert JSON for a matched custom syslog rule:

```json
{
  "timestamp": "2026-06-01T13:51:04.123+0000",
  "rule": {
    "id": "100200",
    "level": 5,
    "description": "Lab2 Sim: Stage 1 — System discovery commands executed",
    "groups": ["custom_soc", "lab_simulation", "lab2", "discovery"],
    "mitre": {
      "id": ["T1082", "T1033"],
      "tactic": ["Discovery"],
      "technique": ["System Information Discovery", "System Owner/User Discovery"]
    }
  },
  "predecoder": {
    "program_name": "lab2-attacker",
    "hostname": "s1-lab-target"
  },
  "agent": {
    "id": "007",
    "name": "s1-lab-target"
  },
  "full_log": "Jun 01 13:51:04 s1-lab-target lab2-attacker: STAGE:DISCOVERY scanning system - uname id who ps aux executed"
}
```

Filter in Wazuh Dashboard / OpenSearch:
- `predecoder.program_name: lab2-attacker` — all sim events
- `full_log: *DISCOVERY*` — Stage 1 only
- `rule.id: 100200` — specific rule
